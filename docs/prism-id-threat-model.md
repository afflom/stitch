# Prism id threat and security model

This is the threat model for prism id: `Stitch.PrismId` (`app/src/Stitch/PrismId.lex.tex`), the runtime `src/prism-id.js`, and the protocol in `docs/prism-id.md`. It covers browser, native, mobile and embedded devices.

Each threat is also a row in the official Security facet (`Product.Security`, generated by `scripts/check-facets.mjs`). The row names the threat's asset, its STRIDE category, a qualitative likelihood and impact, the control, the executable test, this document, and the Lean theorems in `Stitch.PrismId` that the control rests on.

Likelihood and impact are conservative engineering judgements, not measured probabilities. A theorem proves the stated rule about the model. It does not prove the cryptography, the browser, or the platform.

## 1. Scope and security objectives

| Id | Objective |
| --- | --- |
| O1 | Only devices the person linked can act for their prism. |
| O2 | Only member devices can read the private boundary. After a member is revoked, it cannot read anything sealed later. |
| O3 | Linking a device needs the person's presence at both devices: an out-of-band channel plus a confirmation they make. |
| O4 | A host can verify, on its own, that an action came from an active device of a prism, within that device's scope, once, for that host. |
| O5 | No account, server, registration, payment or third party is required. A failed component cannot take over the identity. |
| O6 | Every runtime computes the same κ and the same authorization result from the same records. |
| O7 | Observers learn as little as the protocol allows. What they can still learn is stated (section 8). |

**Out of scope for this milestone:** recovery after every member device is lost (M4), the substrate transport (M2), foundry frame integration (M3), and post-quantum cryptography (section 10).

## 2. System decomposition

| Element | Kind | Holds | Trust |
| --- | --- | --- | --- |
| Member device | Process: browser tab, native app, mobile app | Non-extractable signing and agreement keys; boundary keyring; prism log | Trusted while linked and not revoked |
| Delegate device | Process, typically embedded | Non-extractable keys, scoped role; no boundary key | Trusted only inside its scope |
| Prism log | Data store, replicated | Signed genesis, bind and revoke records | Integrity from signatures and κ; any holder may relay it |
| Link offer | Data flow over an out-of-band channel | Prism id, role, scope, one-time secret, ephemeral ECDH key, expiry | Confidential until used; integrity from the channel |
| Rendezvous and sync topics | Data flow over the substrate bus | Link request and response; sealed sync messages | Untrusted transport |
| Host | External entity: foundry page, native service, data sink | Replay set, policy | Verifies actions; trusts nothing else |
| Relay or federation node | External entity | Bytes in transit | Untrusted |

### Trust boundaries

- **TB1 Device boundary.** Key handles and keyring stay inside the device process. For browsers, that boundary is the origin (section 7).
- **TB2 Out-of-band channel.** QR code, NFC, USB or serial line, or typed text. It carries the link secret, which is the only secret ever moved this way.
- **TB3 Substrate bus.** Everything that crosses it is either public (signed records) or sealed (AES-GCM).
- **TB4 Host boundary.** A host sees signed actions and the prism log, never boundary keys.
- **TB5 Private boundary.** The set of member devices holding the current boundary key, the "real object" (RO) in OOO terms. Delegates sit outside it.

## 3. Adversaries

| Id | Adversary | Capabilities assumed | Not assumed |
| --- | --- | --- | --- |
| A1 | Network and relay | Reads, drops, delays, replays, reorders and injects bus traffic; runs federation nodes | Breaking P-256, SHA-256, HMAC or AES-GCM |
| A2 | Shoulder surfer | Sees or photographs a link QR code; may answer it from its own device | Seeing the confirmation code on the person's own new device and entering it on the offering device |
| A3 | Device thief | Holds an unlocked member device and every key handle on it | Extracting keys from hardware-backed stores (section 6) |
| A4 | Compromised delegate | Full control of an embedded device and its keys | Member keys |
| A5 | Origin attacker | Runs script in the prism's web origin (XSS, compromised dependency or static host) | Script in a native app or a hardware key store |
| A6 | Malicious host | Receives actions and logs; may collude with other hosts | Breaking signatures |
| A7 | Malicious member prism | A different prism sharing a boundary with this one | Membership in this prism's private boundary |
| A8 | Divergent implementation | A runtime with a canonicalization or validation bug | n/a |

## 4. Assets

| Asset | C | I | A | Notes |
| --- | --- | --- | --- | --- |
| Device signing key | n/a | Critical | High | Non-extractable. Use equals authority. |
| Device agreement key | High | High | Medium | Unwraps boundary keys during linking and rotation. |
| Boundary keyring | Critical | High | High | Extractable so it can be wrapped for the next member; this is a residual (section 7). |
| Prism log | Low | Critical | High | Public by design. Its integrity is authority. |
| Link secret | High until used | High | Low | Single use, expires in 5 minutes by default. |
| Sealed private content | Critical | High | High | Addressed by κ, bound to the prism id. |
| Host replay set | n/a | High | Medium | Host-local. |

| Threat | STRIDE | Adversary | Control | Proofs |
| --- | --- | --- | --- | --- |
| PrismLinkHijack | Spoofing | A2 | One-time secret, expiry, single use. A six-digit code is derived from the secret and the joining device's κ. ## 6. Attack trees

**G1. Act as the person at a host.** This requires an accepted action (O4). Paths:

1. **Forge a device signature.** Requires breaking P-256 (assumption C1).
2. **Use a linked device's key.**
   - 2a. Steal an unlocked device (A3). Bounded by revocation and the host time window; residual until revocation propagates.
   - 2b. Origin script (A5). Residual on browser members (section 7).
3. **Get a rogue device bound.**
   - 3a. Answer a link offer. Needs the secret (A2) and the person's confirmation of the hijacker's code. Blocked by PrismLinkHijack.
   - 3b. Inject a bind. Blocked by PrismRogueBind.
   - 3c. Present a forged genesis. Blocked by PrismGenesisConfusion.
4. **Replay a captured action.** Blocked by PrismActionReplay.
5. **Use a delegate beyond its scope.** Blocked by PrismDelegateOverreach.

**G2. Read the private boundary.** Paths:

1. **Be a member device.** See G1 path 3.
2. **Hold an old member device after revocation.** It reads nothing sealed after the rotation. Content it already held, or content sealed under keys it held, stays readable. That is residual R2.
3. **Read sync traffic.** Sync messages are sealed (C1, C3).
4. **Compromise a delegate.** A delegate holds no boundary key.
5. **Unwrap a rotation or link wrap.** Needs the member's agreement key, or the ephemeral key together with the secret.

**G3. Lock the person out.** Paths:

1. **Revoke every device.** Needs a member device (A3). Mutual revocation revokes the thief as well. Recovery is M4 (residual R4).
2. **Flood or withhold sync.** Bounds apply. Devices stay authoritative offline, and merge converges once traffic resumes.
3. **Withhold a rotation.** The device refuses to seal and keeps reading old content.

## 7. Device classes and their specific threats

All classes speak the same records with the same primitives: P-256 ECDSA and ECDH, HKDF-SHA-256, HMAC-SHA-256, AES-256-GCM, SHA-256. That choice is what lets every class take part: P-256 is the curve that Apple Secure Enclave, Android Keystore/StrongBox, TPM 2.0, WebCrypto and common secure elements (ATECC608, SE050, OPTIGA) all support.

| Class | Typical role | Key store | Link channel | Class-specific threats | Mitigations |
| --- | --- | --- | --- | --- | --- |
| Browser | Member | WebCrypto non-extractable keys in IndexedDB; origin-scoped | Displays or scans QR | Origin script (A5); storage eviction; shared machines | Prefer a native or mobile member as an anchor; revoke on a shared machine; boundary keyring is the residual |
| Native install (desktop) | Member, or always-on federation peer | TPM 2.0, macOS Keychain or Secure Enclave, Windows CNG | Displays or scans QR; typed code | Malware running as the user; backups that copy key stores | Hardware-bound keys (`protection: platform`); exclude key stores from backup; host attestation policy |
| Mobile app | Member | Secure Enclave or Android Keystore/StrongBox, with user presence | Camera QR; NFC | Device theft with the screen unlocked; malicious accessibility services | User-presence gating on signing; fast revocation from any other member; attestation (App Attest, key attestation) when a host requires it |
| Embedded | Delegate | Secure element, or flash on low-end parts | NFC, USB or serial provisioning, or a QR printed on the device that the member scans | Physical extraction; firmware substitution; no screen to show the code | Delegate role only, with a narrow scope; never a boundary key; secure-element keys; the confirmation code is shown on the member device, compared with a code the device prints or emits on its provisioning line |

**Linking without a camera.** The offer URI is plain text. Any channel that reaches the joining device carries it: NFC NDEF, a USB serial line, or typed base64url. The confirmation code always shows where a person can read it. For a headless delegate that means the code it emits on its provisioning line.

## 8. Privacy (LINDDUN)

| Category | Exposure | Status |
| --- | --- | --- |
| Linkability | The same prism id and device keys appear at every host. | Open. Pairwise per-host ids derived from the prism (M3). |
| Identifiability | The prism id is pseudonymous. Content in the private boundary never reaches hosts. | Holds. |
| Non-repudiation (privacy harm) | Signed actions are attributable to the prism. | By design for authority; hosts should not publish them. |
| Detectability | Relays see a topic exists and its traffic volume. | Residual R5. |
| Disclosure | Sealed content needs a member key. | Holds, under C1 to C3. |
| Unawareness | The person must understand a QR code links a device. | The confirmation code makes the step explicit. |
| Non-compliance | No personal data is required to create a prism. | Holds. |

## 9. Assumptions

- **C1.** P-256 ECDSA and ECDH, SHA-256, HMAC-SHA-256, HKDF and AES-256-GCM are secure at their usual strengths.
- **C2.** The platform's random source is sound.
- **C3.** Non-extractable keys cannot be exported by the platform API. Hardware stores resist extraction as their vendors state.
- **C4.** The out-of-band channel reaches the device the person intends. Its confidentiality only needs to hold until the code is confirmed.
- **C5.** Hosts keep a replay set for at least their time window, and their clocks are within that window.

## 10. Residual risks

| Id | Residual | Plan |
| --- | --- | --- |
| R1 | Origin script can use browser key handles and read the extractable boundary keyring while it runs. | Wrap the keyring under a non-extractable key held in a native or hardware member; keep browsers as members of lower assurance (M3 host policy) |
| R2 | A revoked device keeps everything it already held, and any content sealed under keys it held. | Inherent. Re-seal sensitive content after rotation if needed. |
| R3 | A host can link the person across hosts. | Pairwise per-host ids (M3) |
| R4 | Losing every member device loses the prism. A thief can race revocations. | Threshold recovery shares in shared boundaries (M4) |
| R5 | Relays see topic existence, timing, sizes and addresses. | Padding and cover traffic are options for the substrate (M2) |
| R6 | All primitives are classical, and recorded traffic could be decrypted by a future quantum adversary. | Hybrid ML-KEM for wraps once WebCrypto and secure elements ship it; κ (SHA-256) is unaffected |
| R7 | The protection claim is unverified without attestation. | Host-side attestation verifiers per platform |
